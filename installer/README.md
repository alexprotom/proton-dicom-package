# Windows installer

`proton-dicom-package-X.Y.Z-windows-x86_64.exe` - a single-file installer for
the command-line tools, written in Rust like the tools themselves. It is a
port of the Rust DICOM Station installer (same wizard, same update and winget
machinery), trimmed to what a set of console tools needs. No WiX, no NSIS, no
Inno Setup: the wizard is egui/eframe and the system integration is direct
Win32 - shell links through `IShellLink`, registry through `Reg*`, elevation
through `ShellExecuteW`.

**This crate is a separate workspace.** `cargo build --release` in the
repository root builds only the tools and never touches the installer;
building the installer never touches the tools' `target/`.

## Building a release installer

```
cargo build --release                      # 1. the tools, from the repo root
cd installer
cargo build --release                      # 2. pdp-setup.exe + pdp-pack.exe
cargo run --release --bin pdp-pack         # 3. dist/proton-dicom-package-setup.exe
```

Step 3 appends the payload to the setup binary. **The tools are found, not
listed**: every crate under `crates/` that builds an executable (a
`src/main.rs`, or `[[bin]]` tables) is packed, so adding a tool to the
package needs no change here. `pdp-pack --list` shows what would be packed.

| flag | effect |
|---|---|
| `--bin-dir <DIR>` | where the built tools are (default `target/release`) |
| `--no-docs` | leave `docs/` out |
| `--out <FILE>` | write the installer somewhere else |
| `--winget <DIR>` | also write the winget manifests for this installer into `DIR` |
| `--url <URL>` | the download URL recorded in them (default: this version's GitHub release asset) |
| `--release-date <YYYY-MM-DD>` | the release date recorded in them |

A `cargo build`-ed `pdp-setup.exe` has no payload; it then looks for a
`payload/` directory next to itself, which is the convenient way to iterate
on the installer without re-packing.

The installer is not code-signed, so SmartScreen shows the usual "unknown
publisher" warning on first run.

## What the installer does

* **Copies the program** - every tool (`prad-rti-gen.exe`, …), `README.md`,
  `LICENSE.txt`, `docs/` and `pdp-shell.cmd` - into
  `%LOCALAPPDATA%\Programs\Proton DICOM Package` (per user, the default) or
  `%ProgramFiles%\Proton DICOM Package` (all users, asks for elevation).
* **No dependencies.** The tools and the setup program link the C runtime
  statically (`.cargo/config.toml`), so there is no Visual C++ runtime to
  install.
* **PATH** - the program folder is added to `PATH` (on by default; the tools
  are command-line programs), so `prad-rti-gen` runs from any new prompt.
* **The Proton DICOM prompt** - `pdp-shell.cmd`, generated by `pdp-pack`:
  a command prompt with the program folder first on `PATH` that lists the
  tools. It is on the Start menu (*Proton DICOM Package prompt*), optionally
  on the desktop, and - the handy one - on the context menu of every folder
  as **Open Proton DICOM prompt here**: right-click a folder of radiographs
  and convert them where they are.
* **Uninstall and update** - an entry in Apps & features plus
  `pdp-setup.exe` in the program folder: the setup program without its
  payload, which uninstalls (`--uninstall`) and fetches the newest release
  (`--update`, the *Update Proton DICOM Package* Start-menu entry).

Everything created is recorded in `install-manifest.txt`, and the uninstaller
removes exactly what is listed there - nothing else in the folder (your
`prad-rti-gen.toml`, for example), and the `PATH` entry only if the installer
added it.

## Updating

There is one installation per machine, and a newer setup replaces it rather
than adding a second copy. Nothing has to be uninstalled first.

* **Run a newer setup over an installation** and the first page says which
  version is installed where, and offers **Update to X**. The update keeps
  the folder, the scope and the answers given at installation (shortcuts,
  folder menu, `PATH`), and removes the files the new version no longer
  ships - a retired tool, for instance. *Change options* goes through the
  options page first. The same version reinstalls (restores missing files);
  an older one warns before it replaces a newer installation.
* **Other installations are removed.** A copy in another folder, or in the
  other scope, is listed on the first page and removed before the new one is
  written. Untick the box, or pass `--keep-others`, to leave it.
* **Update from the installed program.** *Start ▸ Update Proton DICOM
  Package* (or `pdp-setup.exe --update` in the program folder) looks up the
  newest release on GitHub, downloads its installer, checks it against the
  release's `SHA256SUMS` and runs it. When the installation is already
  current it says so and does nothing.
* **winget**, once the package is published - see below.

Update from the command line, for scripts:

```
"%LOCALAPPDATA%\Programs\Proton DICOM Package\pdp-setup.exe" --update --silent
```

## winget

The release workflow writes winget manifests for every installer it builds
(`proton-dicom-package-X.Y.Z-winget-manifests.zip` on the release) and, once
the package exists in the community repository, submits each new version to
[microsoft/winget-pkgs](https://github.com/microsoft/winget-pkgs) itself.
After that:

```
winget install PDP.ProtonDICOMPackage                  # just me
winget install PDP.ProtonDICOMPackage --scope machine  # all users
winget upgrade PDP.ProtonDICOMPackage
winget uninstall PDP.ProtonDICOMPackage
```

| winget | setup |
|---|---|
| `Silent` | `--silent` |
| `SilentWithProgress` (winget's default) | `--passive` |
| `InstallLocation` | `--dir "<INSTALLPATH>"` |
| scope `user` | `--just-me --no-launch` |
| scope `machine` | `--all-users --no-launch`, run elevated by winget |
| `Commands` | the tools, so `winget search --command prad-rti-gen` finds the package |
| exit codes | 2 `packageInUse`, 3 `cancelledByUser`, 4 `downgrade`, 5 `noNetwork` |

## Command line

```
pdp-setup --silent                              # per user, defaults
pdp-setup --silent --dir "D:\Apps\PDP" --no-folder-menu
pdp-setup --silent --all-users                  # from an elevated prompt
pdp-setup --passive                             # progress window only
pdp-setup.exe --update --silent                 # in the program folder: newest release
pdp-setup.exe --uninstall --silent
pdp-setup --help
```

Over an existing installation, the options on the command line override the
ones it was made with; everything not mentioned stays as it was. The install
flags are `--dir`, `--all-users`, `--just-me`, `--no-path` / `--add-to-path`,
`--no-start-menu`, `--desktop-shortcut` / `--no-desktop-shortcut`,
`--no-folder-menu`, `--no-launch`, `--keep-others` and `--allow-downgrade`.

| exit code | meaning |
|---|---|
| 0 | done, or `--update` found nothing newer |
| 1 | failed |
| 2 | a tool is running from the folder being written or removed |
| 3 | cancelled |
| 4 | a newer version is installed (`--silent` / `--passive` without `--allow-downgrade`) |
| 5 | the newest release could not be looked up or downloaded |

## Source map

| file | contents |
|---|---|
| `src/main.rs` | argument parsing, mode dispatch, elevation re-launch |
| `src/product.rs` | product identity, tool list format and version comparison, shared with `pdp-pack` |
| `src/plan.rs` | install options, default paths, the prompt command, exit codes |
| `src/existing.rs` | finding installed copies and reading back their options |
| `src/payload.rs` | the appended-zip payload format and extraction |
| `src/install.rs` | the install and update steps and the manifest |
| `src/update.rs` | the newest GitHub release: lookup, download, SHA-256 check, hand-over |
| `src/uninstall.rs` | manifest-driven removal, self-deleting uninstaller |
| `src/ui.rs` | the egui wizard |
| `src/console.rs` | text-mode / silent front end |
| `src/win/` | shell links, registry, known folders, console attach |
| `src/bin/pack.rs` | `pdp-pack`: finds the tools, builds the shippable installer and its winget manifests |
